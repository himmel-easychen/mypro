# RAG 评估指标和验收标准（2026-09-13）

## 1. 适用范围

本标准针对当前 50 条评估集和 P1 检索闭环，覆盖真实向量、关键词/精确召回、融合、parent 扩展、拒答和来源验证。
本标准不把 Tool、Graph、Writer、Review 或投标协作 Workflow 纳入 P1 检索验收。

## 2. 已确认的评估指标

### 2.1 主检索指标

1. `Recall@K`：`|返回候选 ∩ 相关 chunkId| / |相关 chunkId|`，不能只统计命中一个。
2. `Hit@K`：前 K 名中至少出现一个相关 Chunk。
3. `MRR@K`：第一个相关候选排名的倒数，主要衡量首条证据排序。
4. 固定报告 `K=1、3、5、10`，本轮只保留三项主门禁：`Recall@5`、`MRR@5`、`nDCG@10`。用户口中的 `MMR@5` 按既有约定解释为 `MRR@5`（Mean Reciprocal Rank）；若要验收 Maximal Marginal Relevance，需要另定义多样性真值。

### 2.2 当前 50 条增强样本指标

1. `MultiHopComplete@5`：多跳题的全部相关 Chunk 是否进入 Top5。
2. `NumericAccuracy`：金额、数量、比例、日期、单位和比较方向完全正确。
3. `SourceLocationAccuracy`：文档、页码、表格、行列与真值一致。
4. `RefusalAccuracy`：不可回答问题是否明确输出“未提及”并拒绝编造。
5. `ContextTargetPreservation`：混淆上下文中是否仍使用目标证据。
6. `DistractorAdoptionRate`：是否采纳干扰 Chunk 的错误信息，越低越好。
7. `CitationAccuracy`：回答中的 Chunk、页码和表格引用是否支持结论。

### 2.3 诊断指标

1. `nDCG@10`：当前只有二值相关性，按相关 Chunk 的理想排序计算，本轮纳入硬门禁。
2. 检索成功率、空结果率、重复 Chunk 率和 parent 上下文膨胀率。
3. provider p50/p95 延迟、总检索 p50/p95 延迟和降级次数。

`unanswerable` 不纳入普通 Recall/MRR 分母，只纳入拒答和干扰采纳指标。

## 3. P1 必须补充的验收项

### 3.1 数据真实性

- `chunk_embedding` 全量使用 `qwen3.7-text-embedding`、1024 维真实向量。
- 不存在遗留 mock 向量、孤儿 child 或无法关联 parent 的结果。
- 评估集中的 `relevant_chunk_ids` 均能在当前数据库找到。
- 评估使用真实 PostgreSQL/pgvector 数据，不以单元测试替代运行态验收。

### 3.2 Provider 契约

- Vector、Keyword、Exact 三路均能独立返回候选、rank、score 和来源字段。
- 统一返回 `chunkId`、`parentChunkId`、`documentId`、source file、location 和 provider scores。
- 支持 document、page、block type、table 等过滤条件。
- 数字、金额、日期、项目编号和条款号能走精确匹配路径。

### 3.3 融合与结果正确性

- 相同 `chunkId` 的多路结果只能保留一个候选。
- RRF 公式、`rrf_k`、provider 分数和最终排序可复现。
- 融合后再做 parent 扩展，不得每路重复扩展。
- parent 回填必须使用真实 `parentChunkId`，不得重新文本搜索猜测。
- 结果中不得出现重复 Chunk、错误文档或错误页码。

### 3.4 降级与可恢复性

- ES/Keyword 不可用时，Vector + Exact 仍可返回结果。
- Embedding 不可用时，Keyword + Exact 仍可运行。
- Exact 无结果时保留其他路结果。
- reranker 超时或失败时使用 RRF 结果。
- 三路均失败时返回明确失败状态，不返回伪造候选。

### 3.5 评估与追踪

- 50 条评估集能一键执行并生成 JSON 报告。
- 报告同时输出总体值和 basic、multi_hop、compare_mutation、context_confusion、unanswerable 分项值。
- 每个失败样本保存 query、期望 Chunk、返回 Chunk、答案、trace ID 和失败原因。
- 日志至少包含 query_type、enabled_providers、provider_latency、provider_failure、candidate_count、rrf_k、final_chunk_ids、total_latency。

### 3.6 API 与运行态

- `GET /api/rag/search` 返回稳定结构并兼容旧调用。
- `GET /api/rag/embedding-audit` 可证明向量状态。
- 服务重启后仍能检索同一批数据。
- `mvn -q test` 全部通过；评估 Runner 通过门禁；前端构建通过。

## 4. 第一版建议门禁

| 指标 | 初始门槛 |
|---|---:|
| Recall@5（answerable） | ≥ 0.90 |
| MRR@5（用户称 MMR@5） | ≥ 0.80 |
| nDCG@10（answerable） | ≥ 0.80 |

以上是首轮基线门槛；跑出真实报告后，允许根据误差分析调整，但必须保留历史基线。

## 5. 验收顺序

1. 验证语料、真实向量和评估集 ID。
2. 分别验收 Vector、Keyword、Structured，并记录各路与 Auto/RRF 的分层结果。
3. 验收去重、RRF、parent 扩展和过滤条件。
4. 验收四类增强样本指标。
5. 验收降级、日志、重启恢复和 API 兼容性。
6. 运行完整评估并将报告路径和门禁结果回写项目状态。
